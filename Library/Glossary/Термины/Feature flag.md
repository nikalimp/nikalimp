# Feature flag

**English:** Feature Flag
**Категория:** [[Глоссарий — Product]]
**URL:** nikalimp.ru/glossary/feature-flag

## Определение

Feature flag (фича-флаг, переключатель функции) — это условие в коде, которое включает или выключает возможность продукта без нового релиза. Разработчик выкладывает код вместе с флагом в выключенном состоянии, а включает функцию позже, когда это нужно бизнесу.

Идея разделяет два события, которые раньше были одним: [[Деплой]] (код попал на сервер) и релиз (пользователи увидели новую [[Фича|фичу]]). Раньше выпуск функции означал выкатку всей версии, и откат требовал нового деплоя. Теперь флаг можно выключить за секунды, не трогая код.

Технически флаг — это обычная проверка вида «если флаг включён, показать новый блок, иначе старый». Значение хранят в конфигурации, базе данных или в сервисе управления флагами. Для флага можно задать правила: включить для сотрудников, для 5% пользователей, для одного города или для конкретного тарифа.

### Для чего используют
- **Постепенный запуск.** Новую функцию открывают небольшой доле аудитории и следят за ошибками и метриками. Если всё хорошо, долю увеличивают.
- **Быстрый откат.** При сбое флаг выключают, не дожидаясь исправления и новой сборки.
- **Эксперименты.** Флаги лежат в основе [[A-B-тест|A/B-тестов]]: разным группам показывают разные варианты.
- **Доступ по тарифу.** Платные возможности включаются только для оплативших клиентов.
- **Работа в одной ветке.** Незаконченную функцию можно держать в основной ветке выключенной, не создавая долгоживущих веток и конфликтов при слиянии.

### Типичные ошибки
- Не удалять старые флаги. Через год в коде десятки проверок, и никто не помнит, какие из них нужны. Для каждого временного флага заводите задачу на удаление.
- Накапливать вложенные флаги: комбинации растут, и тестировать их все невозможно.
- Хранить флаги так, что их значение нельзя быстро изменить в проде.
- Не тестировать оба состояния флага.
- Держать в клиентском коде флаги, раскрывающие секретные планы: пользователь может увидеть их в исходниках.

### Кому и когда это нужно
Практика полезна сервисам с частыми релизами и большой аудиторией. Для небольшого сайта часто достаточно простой переменной окружения, а полноценные платформы флагов нужны, когда продукт развивается командой и запускает много экспериментов.

При этом флаги требуют дисциплины: у каждого должны быть владелец, назначение и дата, когда его планируют убрать.

Хорошая практика — записывать в описании флага, кто его создал, зачем и когда его нужно убрать.

### Частый вопрос
**Чем feature flag отличается от ветки в Git?** Ветка разделяет код на этапе разработки, а флаг управляет поведением уже выложенного кода во время работы. Поэтому флаг позволяет включить функцию для части пользователей и мгновенно выключить её, чего ветка сделать не может.
