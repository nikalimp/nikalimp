# Pull request

**English:** Pull Request
**Категория:** [[Глоссарий — Веб-разработка]]
**URL:** nikalimp.ru/glossary/pull-request

## Определение

Pull request (PR, пулл-реквест) — это запрос на включение изменений из одной [[Ветка|ветки]] репозитория в другую, обычно в основную. Он позволяет команде обсудить и проверить правки, прежде чем они попадут в проект.

Типичный процесс выглядит так. Разработчик создаёт отдельную ветку, вносит изменения и отправляет её в [[GitHub (термин)|GitHub]]. Затем открывает pull request: описывает, что изменено и зачем. Коллеги смотрят код построчно, оставляют комментарии и просят исправить. Параллельно запускаются автоматические проверки: тесты, линтер, сборка (см. [[CI-CD]]). Если всё хорошо, изменения вливают в основную ветку. В GitLab то же самое называется merge request.

Для сайтов и сервисов PR стал стандартом: любая правка проходит ревью, а история остаётся в репозитории. Это снижает число ошибок и помогает не потерять причину изменения.

Самый частый сценарий для сайтов: правка проходит ревью, после слияния автоматически запускается публикация. Так устроены многие процессы выкладки на GitHub Actions. Заказчик при этом может смотреть PR и видеть, что именно изменилось на сайте, и подтверждать правки перед выходом в продакшен.

### Из чего состоит PR
- Название, которое коротко объясняет суть.
- Описание: что сделано, почему и как проверить.
- Список изменённых файлов с подсветкой отличий.
- Комментарии ревьюеров и ответы автора.
- Статус автоматических проверок.

### Как оформить хороший PR
1. Делайте небольшие изменения на одну тему: их проще проверить.
2. Пишите название и описание так, чтобы понял человек, не знакомый с задачей.
3. Привяжите задачу, если она есть в трекере.
4. Добавьте скриншоты для визуальных правок.
5. Дождитесь зелёных проверок до запроса ревью.

### Типичные ошибки
- Огромный PR на сотни файлов, который никто не читает внимательно.
- Пустое описание и название вроде «правки».
- Слияние без проверки, когда тесты красные.
- В PR попадают случайные файлы: пароли, ключи, лишние настройки.

### Частый вопрос
**Нужен ли pull request, если разработчик работает один?** Не обязательно, но полезно. PR запускает автоматические проверки до слияния и оставляет понятную историю изменений. Через полгода будет проще вспомнить, почему сделана та или иная правка.
