# Версионирование

**English:** Versioning
**Категория:** [[Глоссарий — Product]]
**URL:** nikalimp.ru/glossary/versioning

## Определение

Версионирование — это система нумерации версий продукта, по которой по номеру видно, что изменилось: добавили функции, исправили ошибки или сломали совместимость.

Номер версии отвечает на вопросы пользователя и разработчика: что у меня сейчас стоит, чем новая версия отличается от старой, безопасно ли обновляться. Без версий невозможно воспроизвести ошибку («у вас версия 2.3.1, а баг исправили в 2.3.2»), откатиться на предыдущее состояние и вести [[Changelog]].

Самая распространённая схема — семантическое версионирование (Semantic Versioning, SemVer). Номер состоит из трёх чисел: МАЖОР.МИНОР.ПАТЧ, например 2.4.1. Правила такие: патч увеличивают при исправлении ошибок без новых функций, минор — при добавлении возможностей с сохранением совместимости, мажор — при изменениях, которые ломают совместимость со старым.

Другие схемы: календарное версионирование (2026.11 — год и месяц выпуска, так нумеруют, например, Ubuntu), порядковые номера сборок и маркетинговые названия вроде «iOS 18». Для API версию часто выносят в адрес: /api/v2/.

### Пример
Приложение сейчас на версии 3.2.0. Разработчики исправили сбой при входе — получилась 3.2.1. Добавили экспорт отчётов в PDF — 3.3.0. Переписали формат данных так, что старые интеграции перестали работать, — 4.0.0.

### Как выбрать схему
1. Если у продукта есть публичный API или библиотека, берите SemVer — пользователям нужна ясность про совместимость.
2. Если продукт обновляется постоянно и клиенты не выбирают версию (веб-сервис), хватит календарных дат или номера релиза.
3. Заведите правило: что считается мажором, что минором, и записывайте его в документации.
4. Привяжите номер к тегу в системе контроля версий и к записи в changelog.

### Типичные ошибки
- Менять номер «на глаз» без правил.
- Выпускать ломающие изменения под минорной версией.
- Не вести changelog, из-за чего номер ничего не объясняет.
- Путать версию продукта с версией документа или версией API.

### Чем отличается от релиза
[[Релиз]] — это событие выпуска версии пользователям, а версия — её обозначение. Один релиз может включать новую версию, а можно выпустить несколько версий внутри одной команды, не показывая их клиентам.

### Кому и когда это нужно
Версии нужны любому продукту, где есть установка у клиента: мобильным приложениям, десктопным программам, библиотекам и API. Для них важно, чтобы разработчики интеграций знали, когда безопасно обновляться. Веб-сервису хватит внутреннего номера сборки, но с ростом команды и клиентов формальные версии всё равно пригодятся для разбора инцидентов.

### Частый вопрос
**Нужно ли версионировать веб-сервис, если он обновляется ежедневно?** Для клиентов не обязательно, но внутренне стоит: номер сборки или дата деплоя помогают найти, какой код работает, и откатиться при ошибке. Версии выводят явно, если у сервиса есть публичный API.
